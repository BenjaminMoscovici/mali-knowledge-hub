# Administration in the V4 Hub

The V4 `/admin` and `/Administration` pages share the Hub's verified-email/password session. The original V3 administration service remains unchanged as a fallback for existing allowlisted administrators.

Existing server-configured `MKH_ADMIN_EMAILS` addresses bootstrap access. Invited administrators are stored by authenticated user UUID and current verified email in server-only database tables. Editable profile metadata and browser flags never grant permissions. Every administrative API request re-verifies the provider identity and queries current access. No administrator or invitation is seeded by the migration.

An existing administrator can invite a personal email address. New accounts receive the provider's invitation email; existing confirmed accounts receive a sign-in link without creating a replacement account; existing unconfirmed accounts receive a confirmation resend. All return to the existing exact allowed Hub root. Successful invitation callbacks and pending invitations reached through account email links open the V4 administration page. The recipient chooses their password and explicitly accepts. The server validates verified recipient identity, pending status, expiry and the inviter's current authority before password update and again in the atomic grant transaction. Failed password changes, failed email requests, expired/revoked/used invitations and mismatched identities grant no rights. Existing account UUIDs and saved research stay unchanged.

Invitations expire after seven days; provider email links have their own shorter lifetime. Administrators can revoke an open invitation and issue another. The database serializes acceptance to prevent replay. If an invitation is revoked between password update and final acceptance, the password update is reported honestly and no role is granted. A delivery error leaves a failed invitation; uncertain delivery never grants access automatically. An inviter losing authorization invalidates unaccepted invitations. Changing an accepted administrator's email invalidates the stored email binding until separately authorized again.

The integrated Supabase mail service and its subjects/templates are retained per the owner's decision. Its documented recipient and rate limits still apply. No email is sent merely by deployment, and no real recipient is selected by the agent. End-to-end email/password acceptance needs a user-controlled mailbox and password entry.

Administrators can upload supported documents through the existing private-original, checksum, extraction, embedding and atomic publication pipeline. Only validated ready documents enter public retrieval. Original filenames, uploader UUIDs, timestamps and ingestion state remain auditable. Recent jobs include error/metadata/quality inspection and retry/reprocess actions. CSV/TSV intake is document-text indexing, not structured observation ingestion. The public-Hub publication purpose is explicit before upload. The new UI does not replace the legacy V3 metadata correction interface.

Data-feed registration records a public HTTPS address and description for connector review. It performs no fetch, no API activation, no scheduling and no evidence publication. The UI explicitly labels this state; a URL alone is not a working data stream. Embedded credentials, query parameters, fragments and literal private hosts are rejected. A future connector must separately validate licensing, provenance, geography/indicator semantics, endpoints and network safety.

All four new tables use RLS and have no `anon`/`authenticated` table grants or policies. RPCs are `SECURITY INVOKER`, fixed-search-path, executable only by `service_role`; privileged credentials remain server-side. The existing server role receives narrowly scoped SELECT access to only `auth.users.id`, `email` and `email_confirmed_at` for canonical identity checks. It receives no password/token-column access and no Auth mutation grant. No schema or ACL of existing research/evidence tables changes. Invite acceptance, creation/delivery/revocation, source requests and document operations are auditable. The additive schema is retained on code rollback; do not drop populated authorization/audit tables as a rollback step.

Qualification includes fake-provider API/frontend tests and a rolled-back database test using synthetic identities only. It covers recipient binding, confirmed-email checks, live inviter authority, expiry, revocation, replay, normal-user denial, service-only RPC/table access and audit creation. This does not certify real mailbox receipt, real password choice, authenticated saved-history acceptance, arbitrary feed connectivity or cold/concurrent processing reliability.
